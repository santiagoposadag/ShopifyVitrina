Vitrina · architecture as built

Two doors, one inbox

A WhatsApp-native inventory assistant for a Shopify store. Every inbound message — from a person or from another agent — lands in the same durable table and travels the same path. What differs is only who is asking, and that is decided by a row in a database, never by anything the message says.

The path a message takes

Two entry points, both authenticating before anything else. They converge on one inbox because everything after that point — the retry budget, the ordering guarantee, the crash replay — is a property of the table, not of the door.

The queue serializes by conversation, and that is what makes claiming a batch safe: two batches for one conversation must never overlap. Delivery is at-least-once, so a failed batch returns its rows to pending and retries on a backoff until the attempt budget is spent.

Where state actually lives

This is the fact that reorganizes everything else: the catalog is Shopify. There is no local products table, no storefront of our own, and no sync layer. SQLite holds only what Shopify has nowhere to put.

The role boundary

Role comes from the assignments table, read on every message, so a change takes effect with no restart. It is never read from what the person writes — the sales persona explicitly ignores “I am the owner”. The boundary is enforced twice, and both layers have pinning tests.

No role is consulted anywhere in the tool registry. The served set is the agent definition’s own tools[] — a property of the agent, never of the caller. A customer reaching an owner tool would be a stranger repricing a live store.

Agents are data, not code

Each assistant is a directory on disk, validated at boot. A typo in a definition, a prompt naming a tool it was never given, or a knowledge document that does not fit its declared budget fails the deploy rather than the first message.

Components, by what they own

Transports — whatsapp/

Two implementations behind one WhatsAppChannel interface, chosen by WHATSAPP_PROVIDER. That seam is what makes the choice a variable and a restart rather than a revert.

  • cloud.ts · Meta Business Cloud API — currently live
  • bridge.ts · Go sidecar, paired as a linked device

Shopify layer — shopify/

  • client.ts · mints its own token, retries throttling
  • catalog.ts · the operations
  • rank.ts · Spanish relevance scoring
  • cache.ts · a corpus for ranking, not a mirror

Two failure shapes both arrive as HTTP 200 here: cost throttling, and a business-rule rejection returned as a response field.

Tools — tools/

A registry keyed by definition, plus five packs that state policy. What they may reach is assembled once in the composition root: catalog, leads, media, knowledge, agents.

Ops levers — data/*.ts

  • role-assignments · who is an owner, now
  • agent-credentials · the a2a door
  • purge-sessions · drop customer history
  • backup · consistent snapshot under writes

How the code is layered

The pipeline above is how a message moves. This is how the modules depend — a different cut of the same system. It is modular by responsibility with ports at the boundaries that matter, not a strict layered architecture, and the figure says so rather than drawing it cleaner than it is.

What moved today

Three value imports pointed backwards: a concept owned by more than one layer, defined inside one of them. Each now lives in a shared leaf both sides read.

data/purge.ts isAgentConversationKey inbox/envelope.ts → a2a-protocol.ts
tools/packs/agents.ts MAX_HOP inbox/a2a.ts → a2a-protocol.ts
knowledge/store.ts undeclaredToolMentions agent/definition.ts → tool-mentions.ts
a2a-protocol.ts holds the agent-to-agent vocabulary whole — the prefix, the key minter, the predicate and the hop cap. Moving only the predicate would have put a format's writer in one file and its reader in another, which is worse than the leak it closes. Relocations only: the prefix is still a2a:, the cap is still 3, and every existing assertion passed unchanged.
Not closed: two cycles run through tools/registry.ts. It reads tool-name constants from agent/definition.ts while the runtime builds the tool server from the registry, and it registers the knowledge tool while that tool uses the registry's shared factory. Both are shallow and both are real; they are recorded as debt rather than drawn away.

The test console

Built so the store owner can experience both flows from their own phone during the manual test period. It is designed to be removed by deleting files and rows, and it announces itself in the boot log on every restart.

Its containment argument is that there is nothing to contain: there is no phone parameter anywhere in its surface. The phone comes from the roster row the bearer token matched, so no request can name another number — there is no field to put one in. An empty roster answers 404 on every path, including the page itself.
